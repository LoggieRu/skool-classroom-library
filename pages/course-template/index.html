What is an API?

Definition: An API (Application Programming Interface) exposes a service that developers can consume to interact with an application.

The Restaurant Analogy

Imagine you're sitting at a restaurant. You don't walk into the kitchen to cook your meal — you ask the waiter. The waiter takes your request to the kitchen and returns the result to your table.

Client (You)
→
API Interface (Waiter)
→
Application (Kitchen)

Menu = Documentation. It tells you what you can request and how to request it.

Why the Interface Matters

The interface abstracts complexity. Without an API, you'd need to "go into the kitchen" — meaning you'd have to deal with internal server details just to read or update data.

✅ APIs give you an easy, standardized way to access application data and functionality.

Example: Google Sheets

Google Sheets provides an API with services such as "get all data in a sheet" or "update rows." In n8n, you can consume these services via nodes to read and write spreadsheet data without doing it manually.

Key Terminology

📤

Request

The message you send through the interface to ask the application to do something.

📥

Response

The message the application returns back through the interface with the result.

🧑‍💻

Client & Server

You (or n8n) is the client. The API endpoint you call represents the server side.

HTTP Requests

Most APIs you'll use in automations are built on HTTP. In n8n, the HTTP Request node mirrors these concepts directly.

The 4 Components of an HTTP Request

🔗

1) URL

The location of the resource you want to access (data, file, page, etc.).

Contains a scheme (https), host, path, and optionally port + query parameters.

🏷️

2) Method

The action verb for what you want to do.

  • GET — retrieve information
  • POST — send information
  • Less common: DELETE, PUT, PATCH
🧾

3) Headers

Extra context about your request (format, device type, language, auth, etc.).

Example: Accept: application/json

📦

4) Body

The payload you send (usually for POST requests).

Example: firstName, lastName, email from a form submission.

Credentials & Authentication

Most APIs require authentication so only authorized users can read/write data. Credentials can be included in different ways:

  • Query parameter: ?api_key=YOUR_KEY
  • Header: Authorization: Bearer YOUR_KEY
  • OAuth: the "Sign in with Google" style authorization flow
⚠️ If you get a 401 error, authentication is the first thing to check.

HTTP Responses

The 3 Components of an HTTP Response

🔢

1) Status Code

A 3-digit number indicating success or failure.

  • 200 — OK / success
  • 401 — Unauthorized (auth issue)
  • 404 — Not found
  • 500 — Server error (try again later)
🧾

2) Headers

Context about the response (content type, length, caching/expiry, etc.).

📄

3) Body

The returned data itself — often JSON, sometimes HTML, or even binary files.

💡 2xx = success  |  4xx = fix the request  |  5xx = server problem

Webhooks (Reverse APIs)

The Doorbell Analogy

If you're waiting for friends, you can either check the door every few minutes (polling), or you can wait for the doorbell to ring (webhook).

Polling
→
"Any new event yet?"
→
Repeat (waste + delay)
Webhook
→
Event happens
→
Instant notification

Example: Stripe Payments

If you need to know the moment a payment is made, polling would mean repeatedly asking Stripe, "Is there a new payment?" A webhook allows Stripe to notify you immediately when a payment occurs.

What You Need to Set Up a Webhook

  • A URL — the address where the service will send the webhook data
  • An n8n Webhook node — to receive the data and trigger the workflow
✅ Use webhooks when you want workflows to trigger instantly based on events in another system.

📝 Quick Reference Summary

Concept What it Means Practical Use in n8n
API Interface to access application data/services Use app nodes or HTTP Request node
Documentation Rules for how to call the API Choose endpoint, method, and fields correctly
HTTP Request URL + Method + Headers + Body Build custom integrations beyond standard nodes
Status Codes Success/failure signal from server Debug: 2xx OK, 4xx fix request, 5xx retry
Webhook Event-driven "push" notification Trigger workflows instantly when something happens
Polling Repeatedly checking for updates Works, but slower and more resource-heavy
